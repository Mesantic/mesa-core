# Warehouse behavior — measured, not documented

Generated by `mesa_core.conformance` (SPEC_103 Slice 8). Do not hand-edit — re-run
the harness instead.

Every row below is one of two things:

- **VERIFIED** — the warehouse was run and behaved as the spec's DOCUMENTED row
  claims. The date and warehouse version are recorded so the row is reproducible.
- **FALSIFIED** — it behaved differently. The `Actual` column says what happened,
  and the slice that depends on the row needs revisiting.

**SKIPPED** is not a pass. A check that couldn't run is a gap in the evidence, and
it's counted separately so "0 falsified" is never read as "all good".

Slice 8a (DuckDB) runs in CI and is free. It is a regression suite for mesa-core's
own compiler, **not** a stand-in for cloud behavior — DuckDB's `concat` ignores
NULL and `/` returns a double, which is not what SQL Server does. The cloud rows
wait for Slice 8b, which costs about $1/hr per warehouse and needs approval per run.

### What each row means

- **`NULL_KEY`** — DuckDB is NOT SQL Server. This row does not settle the T-SQL NULL-hash question — Slice 8b does. It pins DuckDB's behavior so a compiler change that starts relying on it is caught.
- **`TRAILING_SPACE`** — A collision here means two distinct natural keys produce one ID. The doctrine says normalize before hashing; this proves the warehouse doesn't do it for you.
- **`CASE_VARIANT`** — Case-folding before hashing is the author's job, not the warehouse's. A collision here would mean the warehouse folds case for you, which would make IDs unstable across collations.
- **`INT_RATIO`** — DuckDB differs from Redshift and SQL Server here, which is why Slice 7's integer-division rule is DOCUMENTED until 8b runs it on those two. A ratio metric that relies on truncation would give a different number on DuckDB than on T-SQL.
- **`MICROSECOND`** — Truncation to seconds silently collapses two events into one, which changes a count without changing a row count.
- **`MIXED_CASE_KEYS`** — DuckDB preserves the literal key. Snowflake's wildcard OBJECT_CONSTRUCT does NOT — that's the bug the explicit key/value form in the wide render exists to avoid.
- **`BOOLEAN`** — DuckDB allows MIN/MAX on BOOLEAN. T-SQL BIT is DOCUMENTED not to — that's why the signal macro needs the count-only fallback rather than assuming the single-scan form works everywhere.
- **`ALL_NULL`** — A dead column must fail the generated signal test. If this row ever reports non_null > 0 the fixture drifted, not the rule.
- **`CONSTANT`** — Warn, not fail — a constant column is suspicious, not always wrong. ``allow_constant`` silences it for a column that's legitimately constant.
- **`IDENTITY_EXPR`** — The only row that runs compiler output. A FALSIFIED here means the canonical ID formula changed, which rewrites every ID on DuckDB — SPEC_103 Slice 2 says that must never happen silently.
